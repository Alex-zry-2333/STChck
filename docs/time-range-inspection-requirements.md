## 1. 需求理解

当前系统的监控查询固定为"最近 `check_interval_minutes` 分钟"窗口的实时视角（`src/db.rs:743` `query_monitor_data` / `src/db.rs:1011` `query_monitor_data_doris`）。前端图表接口 `/api/chart/alarms`、`/api/chart/values`（`src/main.rs:969,1007`）目前只返回**模拟数据**（`src/monitor.rs:753,780`）。

"时间段监察"指：**用户指定起止时间范围，系统对该时段内的历史数据做回顾性监察分析**，回答"那段时间里，各站/各设备的数据上报情况到底怎么样"——这是与实时窗口互补的历史视角。

典型使用场景（推测，需确认）：

- 值班交接/事后追溯：核查某时段（如昨夜 20:00–今晨 08:00）哪些站点缺报、缺在哪些分钟；
- 故障复盘：某站告警后，回看告警前后各设备的到报与数值变化；
- 数据质量例行检查：对昨天全天做一次到报率巡检。

## 3. 功能分解（初步）

按层拆为四大块，编号供后续任务拆分引用：

- **F1 数据查询层**（`src/db.rs`）：时段聚合查询——按站/设备统计时段内应有分钟数 vs 实有条数（到报率）、缺报分钟清单、首末到报时间。Doris 走文本协议内联（复用 `escape_sql_string`，`src/db.rs:108`）；MySQL 走 `?` 参数化；SQLite 模拟模式提供降级数据。
- **F2 业务逻辑层**（`src/monitor.rs`）：缺报时段合并（连续缺报分钟合并为区间）、时段内告警时间线（对时段内 ST 包逐条 `parse_st_packet`，量大需限量/抽样策略）、数据模型（`src/models.rs` 新增监察响应结构）。
- **F3 API 层**（`src/main.rs`）：新增 `GET /api/inspection?start=&end=&station=`（站点可选，缺省全部），参数校验（时间格式、范围上限、分页）。
- **F4 前端**：时间范围选择器 + 监察结果视图（到报率总览表、缺报时段清单、告警时间线图表）。

## 6. 风险预判（设计阶段需展开）

- **R1 大时段全量解析 ST 包的量级**：Doris `data` 列为完整原始帧文本，7 天 × 32 站 × 每站约 25–30 台设备 × 分钟级，行数达百万级。D6 的限量策略 + D9 的分页分块 + D10 的定点解析构成三层防线，设计文档需给出具体上限与 SQL 形态（键集分页 `WHERE data_time > :cursor ORDER BY data_time LIMIT n`，避免 OFFSET 深翻页）。
- **R2 Doris/MySQL 方言差异**：时段过滤的日期函数在两者间不同（Doris 无 `DATE_SUB` 部分用法差异），F1 需两条 SQL 路径，复用现有 `is_doris` 分支模式（`src/db.rs:752`）。
- **R3 模拟模式数据形态**：SQLite `test_data.db` 只有当前时刻附近的模拟数据，时段查询在模拟模式下应返回"按规则生成的合成结果"而非空，保证页面可演示。
- **R4 YPOWR00 特例**：智能电源 ST 包为自定义格式、不符合字典（`tm.c:547`）。本期维持现有解析行为不变，格式适配后续单独讨论。
- **R5 定点解析的校验**：帧头 7 字段为强约定（业务已确认，无需考虑变更）；仍保留轻量校验——定点解析结果与现有 `parse_st_packet` 抽样对拍，作为 QA 验收项。
